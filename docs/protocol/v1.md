# Pervue Native Protocol v1

**Status:** Frozen for implementation (DOC-01)  
**Protocol version:** 1  
**Transport:** Chrome Native Messaging framing with UTF-8 JSON payloads

This document is the normative contract between the Chrome extension and the native host for protocol version 1. It freezes the envelope shape, request correlation rules, event families, event ordering, and deterministic protocol-error behavior. Provider error categories and capability vocabulary are refined by DOC-02 without changing these envelope rules.

Normative terms **MUST**, **MUST NOT**, **SHOULD**, and **MAY** are used as requirements.

## 1. Design rules

1. Every framed payload MUST be exactly one JSON object.
2. Top-level envelope fields are strict. Unknown top-level fields MUST be rejected.
3. The native host MUST never derive a request ID from provider output.
4. Request IDs are opaque correlation identifiers generated by the extension.
5. Provider-specific data belongs inside `payload`; it MUST NOT alter the top-level envelope.
6. An implementation that does not support protocol version 1 MUST fail deterministically rather than guessing.
7. Once a request has emitted a terminal event, the host MUST NOT emit additional events for that request ID.
8. Each Native Messaging frame MUST contain exactly one JSON value; trailing non-whitespace bytes make the message malformed.
9. Protocol-managed JSON objects MUST reject duplicate member names rather than applying last-wins semantics.
10. The protocol version MUST be the integer token `1`; numerically equivalent spellings such as `1.0` or `1e0` are invalid envelopes.
11. Native JSON parsing MUST cap container nesting at 128 levels. A depth overflow while parsing a method payload is `INVALID_PAYLOAD`; a depth overflow elsewhere in the request is `MALFORMED_MESSAGE`.

Native Messaging length-prefix framing, byte limits, partial reads, and allocation bounds are implemented by NAT-02. This document defines the JSON protocol carried inside those frames.

## 2. Request envelope

Every extension → host request MUST use:

```json
{
  "version": 1,
  "type": "request",
  "request_id": "req_01J...",
  "method": "conversation.send",
  "payload": {}
}
```

### Required fields

| Field | Type | Rules |
|---|---|---|
| `version` | integer | MUST equal `1`. |
| `type` | string | MUST equal `"request"`. |
| `request_id` | string | 1–128 characters; opaque; unique among in-flight requests. |
| `method` | string | MUST be a v1 method listed below. |
| `payload` | object | Method-specific body. |

The request ID syntax is intentionally simple: the first character MUST be alphanumeric; remaining characters MAY contain alphanumerics, `.`, `_`, `:`, or `-`.

## 3. Event envelope

Every host → extension event MUST use:

```json
{
  "version": 1,
  "type": "event",
  "request_id": "req_01J...",
  "event": "response.delta",
  "payload": {
    "text": "partial response"
  }
}
```

### Required fields

| Field | Type | Rules |
|---|---|---|
| `version` | integer | MUST equal `1`. |
| `type` | string | MUST equal `"event"`. |
| `request_id` | string or null | MUST match the originating request, except the explicitly uncorrelated cases below. |
| `event` | string | MUST be a v1 event listed below. |
| `payload` | object | Event-specific body. |

`request_id: null` is permitted only for:

- `host.ready`; and
- `response.failed` when the host cannot recover a valid request ID from malformed input.

All other events MUST carry a non-null request ID.

## 4. Request ID semantics

For normal requests, `request_id` MUST be unique among all currently in-flight requests. Reuse after a request has terminated is discouraged and clients SHOULD generate a fresh opaque ID for every new request.

The host MUST echo the request ID byte-for-byte in every event caused by that request.

Cancellation uses a separate control request with its own request ID:

```json
{
  "version": 1,
  "type": "request",
  "request_id": "req_cancel_1",
  "method": "request.cancel",
  "payload": {
    "target_request_id": "req_answer_1"
  }
}
```

This preserves one-to-one request/event correlation for both the original operation and the cancellation command.

## 5. v1 methods

### 5.1 `conversation.send`

Starts or continues a provider-backed conversation.

Minimum payload:

```json
{
  "provider_id": "fake",
  "input": {
    "text": "Explain this page."
  }
}
```

Optional fields:

```json
{
  "conversation_id": "conv_123",
  "search": {
    "backend_id": "brave",
    "count": 8
  },
  "context": {
    "mode": "selection",
    "text": "Selected passage",
    "truncated": false,
    "page": {
      "title": "Example article",
      "url": "https://example.com/article"
    }
  }
}
```

A follow-up MAY include bounded prior dialogue in `input.history`:

```json
{
  "provider_id": "codex",
  "conversation_id": "conv_123",
  "input": {
    "text": "And what happens next?",
    "history": [
      {"role": "user", "text": "What happened?"},
      {"role": "assistant", "text": "A short explanation."}
    ]
  }
}
```

Rules:

- `provider_id` MUST be a non-empty string.
- `input` MUST be an object containing a non-empty string `text`.
- `conversation_id`, when supplied, MUST be a non-empty string.
- `input.history`, when supplied, MUST be an array of at most 32 messages, with at most 128 KiB of total UTF-8 message text. Every item MUST contain only non-empty `text` and `role` equal to `user` or `assistant`. It carries ordered prior dialogue for adapters that cannot resume a native session. Providers MAY use their native session instead when available. The extension's stable conversation ID and any provider's native session ID are separate; the latter is opaque metadata managed by the adapter. A native session that disappears before the turn starts may be retried once with this history.
- `model` MAY be a model ID for the provider to answer with; without it the provider uses its own default. It MUST be 1–128 bytes of ASCII letters, digits, and `.`, `_`, `-`, `:`, `/`, `@`, starting with a letter or digit, so it can never be read as a command-line option; anything else is `INVALID_PAYLOAD`. The host refuses a `model` for a provider that doesn't report `model_selection: true` with `MODEL_SELECTION_UNSUPPORTED` before the provider runs, rather than silently answering with the default. A provider MAY accept model IDs it doesn't suggest (see `provider.status`), and reports one it doesn't recognize as a provider failure.
- `context` MAY be an object with `mode` (`selection` or `page`), non-empty `text`, boolean `truncated`, and `page` containing string `title` and sanitized HTTP(S) `url`. If `context` is present, all of those members are required; an empty or unstructured object such as `{}` is `INVALID_PAYLOAD`. The native host independently bounds and validates these fields before a provider receives them. Unknown context keys remain forward-compatible and do not affect envelope parsing.
- `search` MAY request provider-independent web retrieval before model synthesis. It is an object with optional `backend_id` (default `"brave"`) and optional `count` (default 8, range 1–10). Backend IDs are 1–32 ASCII lowercase letters/digits/`_`/`-`, beginning with a letter. Search execution is separate from the selected AI provider: normalized results are passed to that provider as untrusted reference data and emitted as `response.source` events. Unknown backends fail with `SEARCH_FAILED` / `SEARCH_BACKEND_NOT_FOUND`; retrieval failures use `SEARCH_FAILED`, while model synthesis failures keep their provider error category.

### 5.2 `provider.status`

Requests status for one provider or the known provider set.

Examples:

```json
{"provider_id": "codex"}
```

or:

```json
{}
```

The host emits zero or more `provider.status` events followed by `response.completed`. A non-empty provider registry MUST emit at least one `provider.status` event; an empty registry MAY complete without one. DOC-02 freezes the normalized availability/authentication/capability vocabulary inside each status payload.

### 5.3 `request.cancel`

Requests cancellation of an in-flight request.

Payload:

```json
{
  "target_request_id": "req_answer_1"
}
```

The cancellation request has its own `request_id`.

If cancellation succeeds:

1. the target request eventually terminates with `response.failed` whose normalized code is `REQUEST_CANCELLED`; and
2. the cancellation request terminates with `request.cancelled`, whose payload names the target request.

If the target does not exist, is already terminal, or cannot be cancelled, the cancellation request terminates with `response.failed`.

### 5.4 `conversation.forget`

Removes what the host and the provider keep for one conversation, after the user deletes it.

Payload:

```json
{
  "provider_id": "claude",
  "conversation_id": "conv_0123456789abcdef"
}
```

Rules:

- `provider_id` and `conversation_id` MUST be non-empty strings. `conversation_id` is the ID the host reported in `conversation.created`.
- The host removes its mapping from the conversation to the provider's native session, and the provider's own saved transcript of that session when the adapter can prove the transcript was written for Pervue (for example, because it records Pervue's private working directory). It never removes anything it cannot attribute to Pervue.
- Forgetting is idempotent: a conversation the host doesn't know, or already forgot, completes successfully.
- The host emits `response.completed` when nothing Pervue could attribute to the conversation remains, and `response.failed` (`INTERNAL_ERROR` / `SESSION_FORGET_FAILED`, retryable) when something it found could not be removed. An unknown `provider_id` fails with `PROVIDER_NOT_FOUND`.

## 6. v1 event families

### `host.ready`

Emitted exactly once by each native-host process after initialization and before normal request processing.

```json
{
  "version": 1,
  "type": "event",
  "request_id": null,
  "event": "host.ready",
  "payload": {
    "host_version": "0.1.0-dev",
    "protocol_versions": [1]
  }
}
```

### `provider.status`

Reports one provider status. The envelope and `provider_id` are frozen here; normalized status/capability fields are frozen by DOC-02.

Minimum payload:

```json
{
  "provider_id": "codex",
  "status": {
    "availability": "available",
    "authentication": "authenticated",
    "capabilities": {
      "streaming": true,
      "continuation": true,
      "web_search": "unknown",
      "page_context": true,
      "attachments": false,
      "model_selection": true,
      "cancellation": true
    }
  }
}
```

A provider that reports `model_selection: true` MAY add `status.models`: suggested models for `conversation.send`'s `model`, as `{"id", "label"}` objects (at most 32; `id` a valid model ID, `label` 1–64 characters). The list is suggestions, not the complete set, and is omitted when empty. Consumers that don't use it can ignore it (§9). In this version a provider's suggestions are fixed when the companion is built; listing the models a provider offers at run time would be a later, additive change.

```json
"models": [
  {"id": "sonnet", "label": "Sonnet (latest)"},
  {"id": "opus", "label": "Opus (latest)"}
]
```

### `conversation.created`

Emitted only when `conversation.send` creates a new provider-neutral conversation.

Payload:

```json
{
  "conversation_id": "conv_123"
}
```

### `response.started`

Marks the start of response production.

Minimum payload:

```json
{
  "provider_id": "fake"
}
```

A conversation response SHOULD also include `conversation_id`.

### `response.delta`

Carries the next ordered text chunk.

Payload:

```json
{
  "text": "partial response"
}
```

`text` MUST be a non-empty UTF-8 string. Delta order is significant and MUST be preserved by the extension.

### `response.source`

Carries one normalized source associated with the response. Search sources use a provider-independent shape so popup/full-page rendering does not depend on Brave or on the selected AI provider.

Payload:

```json
{
  "source_id": "src_search_1",
  "data": {
    "id": "src_search_1",
    "backend_id": "brave",
    "title": "Example result",
    "url": "https://example.com/article",
    "snippet": "Bounded plain-text result excerpt.",
    "source_name": "Example",
    "age": "2 days ago"
  }
}
```

Rules:
- `source_id` MUST equal `data.id`.
- `backend_id`, `title`, `url`, and `snippet` are required for web-search sources; `source_name` and `age` are optional.
- URLs MUST be bounded HTTP(S) URLs. Result fields remain untrusted input and MUST be escaped/rendered as data by browser surfaces.
- Duplicate URLs MAY be collapsed deterministically before emission.
- For a search-backed response, emitted source objects are the same normalized source set supplied to the model for synthesis; provider-specific citation formats do not define Pervue source identity.

### `response.completed`

Successful terminal event.

Payload MAY be empty or contain request-specific completion metadata.

### `response.failed`

Failure terminal event for normal requests and protocol validation failures.

Minimum payload:

```json
{
  "error": {
    "code": "INVALID_REQUEST",
    "reason": "UNKNOWN_METHOD",
    "message": "Unsupported method.",
    "retryable": false
  }
}
```

`error.code` is the normalized application-level category. DOC-02 freezes the complete code vocabulary. `reason` is a stable machine-readable subreason; `message` is human-readable and MUST NOT be used for branching logic.

### `request.cancelled`

Successful terminal event for the cancellation control request.

Payload:

```json
{
  "target_request_id": "req_answer_1"
}
```

## 7. Event ordering

### 7.1 New conversation success

```text
conversation.created
response.started
(response.delta | response.source)*
response.completed
```

Rules:

- `conversation.created` MUST occur before `response.started`.
- `response.started` MUST occur exactly once.
- zero or more deltas/sources MAY follow.
- `response.completed` MUST occur exactly once and is terminal.

### 7.2 Existing conversation success

```text
response.started
(response.delta | response.source)*
response.completed
```

`conversation.created` MUST NOT be emitted merely because an existing conversation is continued.

### 7.3 Failure before response start

For schema, version, method, routing, or other preflight failures:

```text
response.failed
```

No `response.started` is emitted.

### 7.4 Failure after response start

```text
response.started
(response.delta | response.source)*
response.failed
```

`response.failed` is terminal.

### 7.5 Provider status request

```text
provider.status*
response.completed
```

A non-empty provider registry MUST emit at least one `provider.status` event before completion. An empty registry MAY emit zero status events and complete immediately.

### 7.6 Successful cancellation

If the target has not emitted `response.started`, its terminal sequence is:

```text
response.failed(code=REQUEST_CANCELLED)
```

If the target has already emitted `response.started`, its terminal sequence is:

```text
response.started
(response.delta | response.source)*
response.failed(code=REQUEST_CANCELLED)
```

The host MUST NOT synthesize `response.started` solely to represent cancellation.

For cancellation request `req_cancel_1`:

```text
request.cancelled(target_request_id=req_answer_1)
```

After the target's terminal cancellation failure event, no additional delta/source/completion events may be emitted for that target.

### 7.7 Forgetting a conversation

```text
response.completed
```

or, if something could not be removed:

```text
response.failed(code=INTERNAL_ERROR, reason=SESSION_FORGET_FAILED)
```

## 8. Deterministic invalid-input behavior

The host MUST distinguish parseability from semantic validity.

### 8.1 Unsupported protocol version

If the input is valid JSON and a valid request ID is recoverable, the host MUST emit protocol-v1 `response.failed` with the same request ID:

```json
{
  "version": 1,
  "type": "event",
  "request_id": "req_bad_version",
  "event": "response.failed",
  "payload": {
    "error": {
      "code": "INVALID_REQUEST",
      "reason": "UNSUPPORTED_PROTOCOL_VERSION",
      "message": "Unsupported protocol version.",
      "retryable": false
    },
    "protocol": {
      "received_version": 2,
      "supported_versions": [1]
    }
  }
}
```

### 8.2 Unknown method

The host MUST emit `response.failed` with:

- the original request ID;
- `error.code = "INVALID_REQUEST"`; and
- `error.reason = "UNKNOWN_METHOD"`.

### 8.3 Invalid envelope or payload

Missing required fields, wrong top-level types, unknown top-level fields, or invalid method payloads MUST emit `response.failed` with `error.code = "INVALID_REQUEST"` when a valid request ID can be recovered.

### 8.4 Malformed JSON and request-ID recovery

When malformed input already contains a valid request ID that the host recovered before detecting the syntax failure, the host MUST echo that request ID byte-for-byte in the resulting `response.failed` event.

When no valid request ID can be recovered, the host MUST NOT invent one. It MAY emit:

```json
{
  "version": 1,
  "type": "event",
  "request_id": null,
  "event": "response.failed",
  "payload": {
    "error": {
      "code": "INVALID_REQUEST",
      "reason": "MALFORMED_MESSAGE",
      "message": "Malformed request.",
      "retryable": false
    }
  }
}
```

The host SHOULD remain alive after a malformed request unless the underlying Native Messaging stream itself is no longer usable.

## 9. Compatibility

Protocol v1 is strict at the envelope level and extensible inside method/event payloads.

- Adding a new top-level field is a protocol-version change.
- Adding a new method or event requires updating the v1 contract and compatibility tests before implementation consumes it.
- Adding optional fields inside an existing payload is allowed when existing consumers can ignore them safely.
- Changing the meaning or type of an existing required payload field is breaking.
- Extension and native host MUST compare supported protocol versions during startup/health handling before relying on newer behavior.
