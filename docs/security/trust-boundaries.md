# Browser/Native Trust Boundary

**Tracker item:** SEC-01  
**Scope:** the controls between the Chrome extension and the native host. Framework §14 lists the requirements; this document records where each one is enforced and tested.

```text
Web page ──untrusted──▶ content script ──▶ extension pages / service worker ──validated protocol──▶ native host ──▶ provider process
```

## 1. Identity: who may start the host

- Chrome starts `com.pervue.host` only for the extension origins listed in its manifest's `allowed_origins`. That list is the identity check at the boundary.
- The manifest is generated by the host itself, never edited by hand:

  ```bash
  pervue-host --print-manifest <extension-id> [<extension-id>...]
  ```

  It lists exact `chrome-extension://<id>/` origins only. Each ID must be 32 characters from `a` to `p`, so a wildcard, a pattern, a full origin, or another scheme is refused with status 64. The `path` is the absolute path the binary was run from, not canonicalized, so installers run it from the path they want registered (PKG-01).
- The host starts only when its caller-origin argument is exactly `chrome-extension://<id>/`, optionally followed by Chrome's Windows `--parent-window=<handle>` flag, and never without one. On Linux, Chromium was observed to pass exactly one argument of that form. The argument isn't authenticated: a local process can pass any well-formed origin. The check therefore keeps the host to Chrome's launch shape, and Chrome's `allowed_origins` check remains what ties the host to Pervue's extension.
- Inside the extension, the service worker serves ask ports only to the extension's own pages. Ports from content scripts, which run inside web pages, are disconnected (EXT-03).
- Registering the production extension ID and verifying packaged manifests belong to PKG-01 and SEC-04.

Code: `native/host/src/manifest.rs`, `native/host/src/main.rs`. Tests: `native/host/src/manifest.rs`, `native/host/tests/cli.rs`.

## 2. Size limits

| Limit | Value | Host | Extension |
|---|---|---|---|
| Native Messaging frame, either direction | 1 MiB | An inbound frame over it ends the host with status 4; an outbound one is never written. | `NativeConnectionManager.send()` measures each request as Chrome sends it (UTF-8 JSON) and refuses one over the limit with `RequestTooLargeError` before the port opens or is used. The popup refuses a question that alone exceeds it. |
| JSON nesting | 128 | Deeper input fails as `INVALID_PAYLOAD` inside a method payload, `MALFORMED_MESSAGE` elsewhere. | — |
| Request ID | 128 characters | IDs outside the grammar fail as `INVALID_ENVELOPE`. | `REQUEST_ID_PATTERN` refuses them before sending. |

The extension checks the frame limit before sending because the host treats an oversized frame as a broken stream and exits, which would fail every request in flight. A refused question reaches the popup as `INVALID_REQUEST` / `REQUEST_TOO_LARGE`.

The values are defined once per language, in `native/host/src/limits.rs` and `extension/src/shared/limits.js`, and recorded in the machine-readable `docs/protocol/native-messaging-v1.json`. Tests on both sides compare their values with that file, and the fuzz-corpus generator reads its frame limit from it.

## 3. Executables and commands

- Nothing from a request is used as an executable path, a shell argument, or a command string. Provider IDs are opaque names compared exactly with the host's provider registry, which holds the `fake` scaffold and the `codex` adapter. IDs that look like paths or shell commands (`/bin/sh`, `../../bin/sh`, `C:\Windows\System32\cmd.exe`, `$(id)`, embedded NUL) are unknown providers: `PROVIDER_NOT_FOUND` / `PROVIDER_NOT_INSTALLED`.
- Each adapter looks for its own fixed executable name, such as `codex`, by platform-controlled rules (PRO-02): the host's `PATH`, then the usual install locations, or instead the directories in `PERVUE_PROVIDER_PATH` when it is set. Relative directories are skipped, so the lookup never depends on the working directory. These are the local user's own settings: whoever can change them can already run code as that user.
- Only the provider process manager (`native/host/src/process.rs`, NAT-04) starts processes. `native/host/clippy.toml` bans `std::process::Command::new` in the host crate, and the manager's single call carries an explicit `allow`, so any other spawn fails CI's Clippy step.
- The manager takes an absolute executable path and an argument array. There is no shell and no `PATH` search, and each argument reaches the provider as its own argv element. Each provider gets its own stdin, stdout, and stderr pipes, never the host's Native Messaging streams.
- The Codex adapter's arguments are fixed, apart from the working directory it chose and, to continue a conversation, the Codex thread ID that Codex itself reported. Thread IDs that could read as an option, or that hold anything but letters, digits, `-`, and `_`, are refused as malformed output. The question goes on stdin, never in an argument, so its content can't become an option. Codex runs with `--sandbox read-only` from an empty working directory. Browser context never reaches Codex yet: a request that attaches page or selection text fails as `INVALID_REQUEST` / `PAGE_CONTEXT_UNSUPPORTED` before Codex runs, so untrusted page content can't steer it.
- `codex login status` prints the account and a masked key, so the adapter reads only its exit status. Codex's stderr and the messages of failed turns are discarded: the extension sees only fixed, normalized errors, and diagnostics record only codes and reasons.
- Pervue conversation IDs are random and map to Codex threads only inside the host, so the extension never sees or chooses a Codex thread ID. An unknown conversation ID fails as `INVALID_REQUEST` / `UNKNOWN_CONVERSATION` without starting Codex.
- SEC-02 hardens provider invocation further, including the environment providers inherit.

Tests: `provider_ids_are_names_not_paths_or_commands` in `native/host/src/host.rs`; `a_relative_program_path_is_refused_before_anything_starts` and `arguments_are_kept_as_separate_elements` in `native/host/src/process.rs`; `path_comes_before_the_usual_locations_and_relative_entries_are_dropped` in `native/host/src/providers/discovery.rs`; and in `native/test_provider/tests/codex_adapter.rs`, `a_question_streams_its_answer_and_opens_a_conversation` (the exact command line, and the question only on stdin), `a_question_travels_through_the_host_as_protocol_events` (neither Codex's stderr nor the question reaches events or diagnostics), `failed_turns_map_to_normalized_errors`, and `an_unknown_conversation_fails_without_running_codex`.

## 4. Validation before work

- The host validates each request completely (framing, JSON syntax, envelope, version, method, and method payload) before routing it. Providers, where work starts, only ever receive validated, typed requests. Test: `invalid_requests_never_reach_a_provider` in `native/host/src/host.rs`.
- The extension checks a request's ID grammar, size, and serializability before the native port opens or is used. A request that fails any of these checks fails on its own; it can't close the port for other requests in flight. The ask bridge also refuses an empty question before building a request.

## 5. Diagnostics

The host's stderr diagnostics (OBS-01) record identifiers, timings, and normalized outcomes. They never copy request content: no prompt text, page context, other payload members, raw frames, or error messages. Every identifier in a record is cut to 128 characters and JSON-escaped, so a request can't forge or split a record. Diagnostics go only to stderr, never into the stdout frames. Tests: `diagnostics_never_copy_request_content` in `native/host/src/host.rs`, and `diagnostics_go_to_stderr_and_never_into_the_frames` in `native/host/tests/cli.rs`.
