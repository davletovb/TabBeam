# Browser/Native Trust Boundary

> **Naming note (2026-09-29):** The application was renamed from **Pervue** to **TabBeam** before release. The one remaining `pervue` below, the `pervue-codex` directory in SEC-02, is history: it names the shared-temp-directory workspace an earlier revision used, before that was replaced and before the rename.

**Tracker items:** SEC-01, SEC-02, SEC-05  
**Scope:** the controls between the Chrome extension and the native host, and between the host and the provider processes it starts. Framework §14 lists the requirements; this document records where each one is enforced and tested.

```text
Web page ──untrusted──▶ content script ──▶ extension pages / service worker ──validated protocol──▶ native host ──▶ provider process
```

## 1. Identity: who may start the host

- Chrome starts `com.tabbeam.host` only for the extension origins listed in its manifest's `allowed_origins`. That list is the identity check at the boundary.
- The manifest is generated by the host itself, never edited by hand:

  ```bash
  tabbeam-host --print-manifest <extension-id> [<extension-id>...]
  ```

  It lists exact `chrome-extension://<id>/` origins only. Each ID must be 32 characters from `a` to `p`, so a wildcard, a pattern, a full origin, or another scheme is refused with status 64. The `path` is the absolute path the binary was run from, not canonicalized, so installers run it from the path they want registered (PKG-01).
- The host starts only when its caller-origin argument is exactly `chrome-extension://<id>/`, optionally followed by Chrome's Windows `--parent-window=<handle>` flag, and never without one. On Linux, Chromium was observed to pass exactly one argument of that form. The argument isn't authenticated: a local process can pass any well-formed origin. The check therefore keeps the host to Chrome's launch shape, and Chrome's `allowed_origins` check remains what ties the host to TabBeam's extension.
- Inside the extension, the service worker serves ask ports only to the extension's own pages. Ports from content scripts, which run inside web pages, are disconnected (EXT-03).
- Registering the production extension ID and verifying packaged manifests belong to PKG-01 and SEC-04.

Code: `native/host/src/manifest.rs`, `native/host/src/main.rs`. Tests: `native/host/src/manifest.rs`, `native/host/tests/cli.rs`.

## 2. Size limits

| Limit | Value | Host | Extension |
|---|---|---|---|
| Native Messaging frame, either direction | 1 MiB | An inbound frame over it ends the host with status 4; an outbound one is never written. | `NativeConnectionManager.send()` measures each request as Chrome sends it (UTF-8 JSON) and refuses one over the limit with `RequestTooLargeError` before the port opens or is used. The popup refuses a question that alone exceeds it. |
| JSON nesting | 128 | Deeper input fails as `INVALID_PAYLOAD` inside a method payload, `MALFORMED_MESSAGE` elsewhere. | — |
| Request ID | 128 characters | IDs outside the grammar fail as `INVALID_ENVELOPE`. | `REQUEST_ID_PATTERN` refuses them before sending. |
| Selection context | 16 KiB UTF-8 | A larger selection is `INVALID_PAYLOAD`. | Capture is truncated/bounded before sending. |
| Readable-page context | 64 KiB UTF-8 | A larger page body is `INVALID_PAYLOAD`. | Extraction and forwarding enforce the same cap. |
| Context page title | 1024 UTF-8 bytes | A larger title is `INVALID_PAYLOAD`. | The context bridge enforces the same cap. |
| Context page URL | 2048 UTF-8 bytes | A larger URL is `INVALID_PAYLOAD`. | Capture strips credentials/query/fragment and enforces the same cap. |

The extension checks the frame limit before sending because the host treats an oversized frame as a broken stream and exits, which would fail every request in flight. A refused question reaches the popup as `INVALID_REQUEST` / `REQUEST_TOO_LARGE`.

The frame limit is defined in `native/host/src/framing.rs` and reexported by `native/host/src/limits.rs`; the other host limits live in `limits.rs`. The extension limits live in `extension/src/shared/limits.js`. All values are recorded in the machine-readable `docs/protocol/native-messaging-v1.json`. Tests on both sides compare their values with that file, and the fuzz-corpus generator reads its frame limit from it.

## 3. Executables and commands

- Nothing from a request is used as an executable path, a shell argument, or a command string. Provider IDs are opaque names compared exactly with the host's provider registry, which holds the `fake` scaffold and the `codex` and `claude` adapters. IDs that look like paths or shell commands (`/bin/sh`, `../../bin/sh`, `C:\Windows\System32\cmd.exe`, `$(id)`, embedded NUL) are unknown providers: `PROVIDER_NOT_FOUND` / `PROVIDER_NOT_INSTALLED`.
- Each adapter looks for its own fixed executable name, such as `codex`, by platform-controlled rules (PRO-02): the host's `PATH`, then the usual install locations, or instead the directories in `TABBEAM_PROVIDER_PATH` when it is set. Relative directories are skipped, so the lookup never depends on the working directory. These are the local user's own settings: whoever can change them can already run code as that user.
- Only the provider process manager (`https://github.com/davletovb/seatline/blob/e021c2acf05132073d82bf3e2149f1ff64f1f49f/seatline-core/src/process.rs`, NAT-04) starts provider processes. `native/clippy.toml` bans `std::process::Command::new` in both core and host, and the manager's single call carries an explicit `allow`, so any other spawn fails CI's Clippy step.
- The manager takes an absolute executable path and an argument array. There is no shell and no `PATH` search, and each argument reaches the provider as its own argv element, spaces, quotes, and shell syntax included. Each provider gets its own stdin, stdout, and stderr pipes, never the host's Native Messaging streams. On Windows, npm installs Codex as a `codex.cmd` launcher, which Windows runs through `cmd.exe`; Rust's standard library quotes each argument for it and refuses any it can't quote safely. Codex's arguments are fixed but for the workspace path and a validated thread ID, and the question never becomes an argument.
- The Codex adapter's arguments are fixed, apart from its workspace and, to continue a conversation, the Codex thread ID that Codex itself reported. Thread IDs that could read as an option, or that hold anything but letters, digits, `-`, and `_`, are refused as malformed output. The question goes on stdin, never in an argument, so its content can't become an option. An application's system prompt (`Turn::system`, which TabBeam does not set) travels the same way, first in that prompt, for every adapter (`a_system_prompt_reaches_every_provider_ahead_of_the_question` in `https://github.com/davletovb/seatline/blob/e021c2acf05132073d82bf3e2149f1ff64f1f49f/seatline-tests/tests/provider_contract.rs` checks the exact prompt and that no command line holds it). Codex runs with `--sandbox read-only`. Browser context is attacker-controlled: the host validates and bounds its structured fields, the prompt labels it as untrusted JSON reference data, and U+0085/U+2028/U+2029 are escaped so page text cannot visually forge TabBeam prompt sections. The host refuses any request that combines browser context with search (`SEARCH_WITH_CONTEXT_UNSUPPORTED`), so page text never gains live web access. Claude receives context the same way, framed by the same prompt builder; its context turns are plain turns, with no built-in tools (`--tools ""`) and MCP blocked, so page text can inform an answer but never make Claude act (`page_context_reaches_claude_as_untrusted_reference_data_with_no_tools`). Context-only turns additionally disable Codex's built-in shell, image viewer, apps/connectors, plugins, hooks, web search, orchestrator MCP, and subagent surfaces (`features.multi_agent=false` and `features.multi_agent_v2=false`) through CLI config overrides, including legacy web-search feature gates as defense in depth. Merely having Codex plugin caches, installed-plugin artifacts, or hook files does not block context. TabBeam fails closed as `INVALID_REQUEST` / `PAGE_CONTEXT_TOOLS_ENABLED` only when the user-level Codex config declares standalone `mcp_servers`, because those servers are not uniformly controlled by the feature gates TabBeam can override. System-managed Codex policy remains an administrator-controlled trust input.
- **Workspace (SEC-02).** Codex runs in, and is pointed at with `-C`, an empty directory in the user's own cache: `~/Library/Caches/TabBeam/codex-workspace` on macOS, `$XDG_CACHE_HOME/tabbeam/codex-workspace` or `~/.cache/tabbeam/codex-workspace` on other POSIX systems, `%LOCALAPPDATA%\TabBeam\codex-workspace` on Windows. Codex follows instructions it finds where it runs: `AGENTS.md` in its working directory and, when a directory above it holds `.git`, in each directory from that one down. Checked with Codex CLI 0.156.1: with `.git` and an `AGENTS.md` two levels up, both that file and one in between reached the model. So anyone who can change the workspace, or any directory above it, can instruct the user's Codex. The workspace used to be `pervue-codex` in the system temporary directory, which on Linux is shared: another user could create it first, or add `.git` and `AGENTS.md` to `/tmp` itself.

  Before every launch, the host checks the workspace (`https://github.com/davletovb/seatline/blob/e021c2acf05132073d82bf3e2149f1ff64f1f49f/platform/src/workspace.rs`). On POSIX, the workspace must be a directory of the user's own, not a link, and the host sets it to mode 0700. Every directory above it, both as named and with links resolved, must belong to the user or root and be writable by its owner alone; a sticky directory such as `/tmp` doesn't qualify. A directory of the user's may also be writable by the user's private group, as on Linux distributions that give each user one and a umask of 002: the user's primary group, named after the user, with no other members listed. Anyone else's group, or a shared one such as macOS's `staff`, doesn't qualify. Every link on the way must belong to the user or root, so no one else can have placed or replaced it, and Codex gets the resolved path, which is the one checked. The check reads owners and permission bits, not access-control lists. On Windows, reading access-control lists would need platform bindings: the workspace must be a directory, not a link or junction, and it is in `%LOCALAPPDATA%`, which Windows keeps private to the user. Without a cache directory, the host makes a new directory with a random name in the temporary directory, which passes only where that is private to the user, as on macOS and Windows. A workspace that can't be created, or that other users could change, stops Codex from starting (`PROVIDER_FAILED` / `WORKSPACE_UNAVAILABLE`).
- **Environment (SEC-02).** A provider process starts with an empty environment and gets only what the host passes on (`platform/src/environment.rs`): the user's home and name, the temporary directory, the text encoding, the session bus and runtime directory where Linux keyrings are found, network proxies, and extra CA certificates; on Windows, also what programs, `cmd.exe`, and Node need to run. The Codex adapter adds `CODEX_HOME`, `CODEX_SQLITE_HOME`, and `CODEX_CA_CERTIFICATE`, and sets `PATH` to Codex's own directory followed by the host's `PATH`. Nothing else reaches a provider. Credentials in the environment Chrome was started from, such as `OPENAI_API_KEY`, `CODEX_API_KEY`, `AWS_SECRET_ACCESS_KEY`, or `GITHUB_TOKEN`, stay behind, and so do variables that change how programs load code, such as `NODE_OPTIONS`, `LD_PRELOAD`, and `DYLD_INSERT_LIBRARIES`. Codex therefore signs in only with its stored login, the one its status check reports, however Chrome was started. Proxy settings are passed on because Codex can't reach its service without them; they can hold a proxy password, which Codex needs as much as the user's other tools do.
- `codex login status` prints the account and a masked key, so the adapter reads only its exit status. Codex's stderr and the messages of failed turns are discarded: the extension sees only fixed, normalized errors, and diagnostics record only codes and reasons.
- TabBeam conversation IDs are random and map to Codex threads only inside the host and its private session files, so the extension never sees or chooses a Codex thread ID. A stored mapping is used only if it holds a valid thread ID. An unknown conversation ID never reaches Codex: without prior dialogue it fails as `INVALID_REQUEST` / `UNKNOWN_CONVERSATION` before Codex starts, and with prior dialogue Codex starts a new thread from that bounded, validated history (CON-03).
- `conversation.forget` deletes files, so its reach is narrow. The extension can only name a conversation; the host alone maps it to a session, and the conversation and session IDs are validated before they touch a path. The host then removes that mapping and only the provider files that name the session and record TabBeam's private workspace as their working directory: Claude Code transcripts under `projects/`, and Codex `rollout-…` session files. Directories are walked without following symbolic links, a link is removed rather than its target, and nothing outside the provider's own directory (`$CLAUDE_CONFIG_DIR` or `~/.claude`, `$CODEX_HOME` or `~/.codex`) is touched.

## 4. Validation before work

- The host validates each request completely (framing, JSON syntax, envelope, version, method, and method payload) before routing it. Providers, where work starts, only ever receive validated, typed requests. Test: `invalid_requests_never_reach_a_provider` in `native/host/src/host.rs`.
- The extension checks a request's ID grammar, size, and serializability before the native port opens or is used. A request that fails any of these checks fails on its own; it can't close the port for other requests in flight. The ask bridge also refuses an empty question before building a request.

## 5. Diagnostics

The host's stderr diagnostics (OBS-01) record identifiers, timings, and normalized outcomes. They never copy request content: no prompt text, page context, other payload members, raw frames, or error messages. Nor do they copy anything a provider wrote: stderr, the sign-in check's output, and the messages of failed turns are discarded unread. Diagnostics go only to stderr, never into the stdout frames.

Identifiers are redacted (SEC-02): a record copies only identifiers TabBeam made itself. A request ID, or a cancellation's target, is copied only in the shape the extension gives every request, `req_` and a random UUID in lowercase hex. A provider ID is copied only if the host serves that provider, and a conversation ID only if the host created that conversation. Anything else a request carries is written as `[redacted]`. Recognizing secrets by their format can't work, since any caller-chosen text could be one, such as a Google `ya29.` token or a password; so no text a caller chose reaches the log, except a UUID in that shape, and no request can forge or split a record. The extension's own logging records only that a callback failed, never its error message or stack (SEC-03).

Tests: `diagnostics_never_copy_request_content` and `identifiers_tabbeam_did_not_issue_are_redacted_in_diagnostics` in `native/host/src/host.rs`; `request_ids_are_kept_only_in_the_extensions_shape`, `identifiers_are_kept_only_when_the_host_issued_them`, and `identifiers_can_neither_forge_nor_split_a_record` in `native/host/src/diagnostics.rs`; `diagnostics_go_to_stderr_and_never_into_the_frames` in `native/host/tests/cli.rs`; the hostile matrix, through the whole host (`native/test_provider/tests/hostile_matrix.rs`) and under the runtime's scheduler (`https://github.com/davletovb/seatline/blob/e021c2acf05132073d82bf3e2149f1ff64f1f49f/seatline-tests/tests/hostile_matrix.rs`), whose fake Codex writes a fake key to stderr in every case; and the live smoke test, which checks its output for credentials before printing it (TST-05).

## 6. Search results (SEC-05)

A web search turn (SRCH-01..04) brings text from pages TabBeam never chose into the host and the browser: result titles, excerpts, and URLs are written by whoever runs those pages, and reach TabBeam through the provider's output. They are handled as untrusted data from start to finish.

- **Normalized once, before the host sees a source** (`https://github.com/davletovb/seatline/blob/e021c2acf05132073d82bf3e2149f1ff64f1f49f/seatline-core/src/search.rs`). A result is kept only with an `http`/`https` URL the browser's URL parser would also accept (a strict subset: an ASCII domain name without punycode labels or a dotted-quad IPv4 address, a valid port if any, no credentials, no whitespace, control, or invisible characters, and at most 4096 bytes once percent-encoded), so a source counted toward grounding is never one the extension then drops; `docs/protocol/fixtures/v1-source-urls.json` is checked by both sides. Its title, excerpt, publisher, and age become single-line plain text (`display_text`): markup tags are removed, a few common HTML entities decoded, control characters, bidirectional marks, overrides, and isolates, and zero-width spaces dropped (so nothing can reorder or hide what's shown; zero-width joiners stay, since emoji sequences need them), and whitespace collapsed; at most 8× a field's limit is ever scanned. Titles are bounded to 512 bytes, excerpts to 4096, publisher and age to 256. A title that is only markup falls back to the URL's host. Each turn keeps at most 20 sources, one per URL, with IDs the host assigns (`src_<provider>_<n>`).
- **Never part of a command or a later prompt.** Nothing from a result becomes a command-line argument: the provider's arguments are fixed per turn (Claude's search turns add only `--tools WebSearch --allowedTools WebSearch`; Codex's add only `-c web_search="live"`), and questions go on stdin. A follow-up continues the provider's own session and sends only the new question; when the session is gone, the rebuilt prompt holds the conversation's message text, never its sources. The extension never sends sources back to the host.
- **Checked again in the extension** (`extension/src/shared/sources.js`). The service worker accepts a `response.source` only if its `source_id` names its data, its IDs match their grammar, and its URL parses as `http`/`https` with a host and no credentials. It bounds the text again by characters (title 300, excerpt 1000, publisher and age 120), removes control and invisible characters, drops repeats by ID or URL, keeps at most 20 per answer, and forwards to the page only the checked copy, which is also all it stores. Only a complete answer keeps its sources, so a failed or stopped one never looks grounded.
- **Shown as text** (`extension/src/shared/source-list.js`). Pages check sources once more before showing them, set every field as a text node, and never parse them as HTML. A source link opens its checked URL in a new tab, with `rel="noopener noreferrer"`. Nothing is fetched to show a source: there are no favicons, previews, or thumbnails.

## 7. Packaged trust boundaries and permissions (SEC-04)

Packaging keeps the browser/native identity boundary explicit on both supported desktop platforms:

- **Exact extension identity.** Both package builders accept only one 32-character lowercase Chrome extension ID using the browser's `a`–`p` alphabet. The native host generates the manifest allowlist itself, so installers do not construct arbitrary origins. macOS installs that generated manifest at Chrome's fixed system location. Windows installs it under `%LOCALAPPDATA%\\Programs\\TabBeam` and registers only `HKCU\\Software\\Google\\Chrome\\NativeMessagingHosts\\com.tabbeam.host`; its host path is the fixed relative filename `tabbeam-host.exe`, which Chrome resolves relative to the manifest.
- **Installer location and input boundary.** The Windows installer keeps binaries separate from runtime state under `%LOCALAPPDATA%\\TabBeam`. Its normal destination is `%LOCALAPPDATA%\\Programs\\TabBeam`, and a `PrepareToInstall` check rejects Inno `/DIR` or `/LOADINF` changes that would move the payload elsewhere. Host/manifest names and the Native Messaging registry key remain package constants. No web page can supply a provider executable path, registration path, install path, or command string.
- **Upgrade and removal boundary.** Windows Restart Manager is enabled for `tabbeam-host.exe`, so reinstalling while Chrome still owns a native port closes the old host before replacement and does not relaunch it standalone. Uninstall relies only on Inno's recorded installed files/registry values: there is no recursive `{app}` deletion. CI writes a sentinel into `%LOCALAPPDATA%\\TabBeam` and requires it to survive uninstall, while the install directory, Native Messaging registration, and Installed Apps entry must disappear.
- **Credential-free release metadata.** macOS and Windows `build-info.json` contain only version/package version, architecture, paired extension ID, and source commit. Provider credentials remain in provider-owned stores. Package build scripts contain no provider API-key inputs.
- **Minimum extension permissions.** The MV3 manifest requests exactly `activeTab`, `contextMenus`, `nativeMessaging`, and `storage`, with no `host_permissions`, `optional_host_permissions`, or `externally_connectable` entry. Those exact permission invariants live in `extension/tests/manifest-smoke.mjs`. HTTP/HTTPS content scripts are present to implement explicit selection/current-page capture; CTX-03/CTX-04 constrain when content is actually collected and sent.
- **Package regression audit.** `packaging/security-audit.mjs` is path-anchored to its own module and checks the packaging-specific invariants: fixed destination enforcement, exact registration identity, no recursive uninstall deletion or run-command sections, explicit x64 build target, case-sensitive extension-ID validation, generated-manifest verification, signing hook presence, and credential-free build inputs. Platform package jobs separately exercise installed registration and the exact extension allowlist.
- **Windows release signing.** `packaging/windows/build.ps1` exposes only an optional Inno SignTool command, not certificate material. `.github/workflows/windows-release.yml` imports a PFX from CI secrets, signs the staged host, generated uninstaller, and installer, verifies the final Authenticode signature, and uploads the release candidate. Unsigned Windows artifacts are CI/internal mechanics builds only; TST-13 requires a signed candidate.

## 8. Covered elsewhere

- Page-context capture intent remains CTX-03/CTX-04; the shared byte limits are enforced on both sides of this boundary and recorded in `docs/protocol/native-messaging-v1.json`.
