# Browser/Native Trust Boundary

**Tracker items:** SEC-01, SEC-02  
**Scope:** the controls between the Chrome extension and the native host, and between the host and the provider processes it starts. Framework §14 lists the requirements; this document records where each one is enforced and tested.

```text
Web page ──untrusted──▶ content script ──▶ extension pages / service worker ──validated protocol──▶ native host ──▶ provider process
```

## 1. Identity: who may start the host

- Chrome starts `com.pervue.host` only for the extension origins listed in its manifest's `allowed_origins`. That list is the identity check at the boundary.
- The manifest is generated by the host itself, never edited by hand:

  ```bash
  pervue-host --print-manifest <extension-id> [<extension-id>...]
  ```

  It lists exact `chrome-extension://<id>/` origins only. Each ID must be 32 characters from `a` to `p`, so a wildcard, a pattern, a full origin, or another scheme is refused with status 64. The `path` is the absolute path the binary was run from, not canonicalized, so installers run it from the path they want registered (PKG-01).
- The host starts only when its caller-origin argument is exactly `chrome-extension://<id>/`, optionally followed by Chrome's Windows `--parent-window=<handle>` flag, and never without one. On Linux, Chromium was observed to pass exactly one argument of that form. The argument isn't authenticated: a local process can pass any well-formed origin. The check therefore keeps the host to Chrome's launch shape, and Chrome's `allowed_origins` check remains what ties the host to Pervue's extension.
- Inside the extension, the service worker serves ask ports only to the extension's own pages. Ports from content scripts, which run inside web pages, are disconnected (EXT-03).
- Registering the production extension ID and verifying packaged manifests belong to PKG-01 and SEC-04.

Code: `native/host/src/manifest.rs`, `native/host/src/main.rs`. Tests: `native/host/src/manifest.rs`, `native/host/tests/cli.rs`.

## 2. Size limits

| Limit | Value | Host | Extension |
|---|---|---|---|
| Native Messaging frame, either direction | 1 MiB | An inbound frame over it ends the host with status 4; an outbound one is never written. | `NativeConnectionManager.send()` measures each request as Chrome sends it (UTF-8 JSON) and refuses one over the limit with `RequestTooLargeError` before the port opens or is used. The popup refuses a question that alone exceeds it. |
| JSON nesting | 128 | Deeper input fails as `INVALID_PAYLOAD` inside a method payload, `MALFORMED_MESSAGE` elsewhere. | — |
| Request ID | 128 characters | IDs outside the grammar fail as `INVALID_ENVELOPE`. | `REQUEST_ID_PATTERN` refuses them before sending. |
| Selection context | 16 KiB UTF-8 | A larger selection is `INVALID_PAYLOAD`. | Capture is truncated/bounded before sending. |
| Readable-page context | 64 KiB UTF-8 | A larger page body is `INVALID_PAYLOAD`. | Extraction and forwarding enforce the same cap. |
| Context page title | 1024 UTF-8 bytes | A larger title is `INVALID_PAYLOAD`. | The context bridge enforces the same cap. |
| Context page URL | 2048 UTF-8 bytes | A larger URL is `INVALID_PAYLOAD`. | Capture strips credentials/query/fragment and enforces the same cap. |

The extension checks the frame limit before sending because the host treats an oversized frame as a broken stream and exits, which would fail every request in flight. A refused question reaches the popup as `INVALID_REQUEST` / `REQUEST_TOO_LARGE`.

The frame limit is defined in `native/core/src/framing.rs` and reexported by `native/host/src/limits.rs`; the other host limits live in `limits.rs`. The extension limits live in `extension/src/shared/limits.js`. All values are recorded in the machine-readable `docs/protocol/native-messaging-v1.json`. Tests on both sides compare their values with that file, and the fuzz-corpus generator reads its frame limit from it.

## 3. Executables and commands

- Nothing from a request is used as an executable path, a shell argument, or a command string. Provider IDs are opaque names compared exactly with the host's provider registry, which holds the `fake` scaffold and the `codex` and `claude` adapters. IDs that look like paths or shell commands (`/bin/sh`, `../../bin/sh`, `C:\Windows\System32\cmd.exe`, `$(id)`, embedded NUL) are unknown providers: `PROVIDER_NOT_FOUND` / `PROVIDER_NOT_INSTALLED`.
- Each adapter looks for its own fixed executable name, such as `codex`, by platform-controlled rules (PRO-02): the host's `PATH`, then the usual install locations, or instead the directories in `PERVUE_PROVIDER_PATH` when it is set. Relative directories are skipped, so the lookup never depends on the working directory. These are the local user's own settings: whoever can change them can already run code as that user.
- Only the provider process manager (`native/core/src/process.rs`, NAT-04) starts provider processes. `native/clippy.toml` bans `std::process::Command::new` in both core and host, and the manager's single call carries an explicit `allow`, so any other spawn fails CI's Clippy step.
- The manager takes an absolute executable path and an argument array. There is no shell and no `PATH` search, and each argument reaches the provider as its own argv element, spaces, quotes, and shell syntax included. Each provider gets its own stdin, stdout, and stderr pipes, never the host's Native Messaging streams. On Windows, npm installs Codex as a `codex.cmd` launcher, which Windows runs through `cmd.exe`; Rust's standard library quotes each argument for it and refuses any it can't quote safely. Codex's arguments are fixed but for the workspace path and a validated thread ID, and the question never becomes an argument.
- The Codex adapter's arguments are fixed, apart from its workspace and, to continue a conversation, the Codex thread ID that Codex itself reported. Thread IDs that could read as an option, or that hold anything but letters, digits, `-`, and `_`, are refused as malformed output. The question goes on stdin, never in an argument, so its content can't become an option. Codex runs with `--sandbox read-only`. Browser context is attacker-controlled: the host validates and bounds its structured fields, the prompt labels it as untrusted JSON reference data, and U+0085/U+2028/U+2029 are escaped so page text cannot visually forge Pervue prompt sections. Context turns additionally disable Codex's built-in shell, image viewer, apps/connectors, plugins, hooks, web search, orchestrator MCP, and subagent surfaces (`features.multi_agent=false` and `features.multi_agent_v2=false`) through CLI config overrides. Merely having Codex plugin caches, installed-plugin artifacts, or hook files does not block context. Pervue fails closed as `INVALID_REQUEST` / `PAGE_CONTEXT_TOOLS_ENABLED` only when the user-level Codex config declares standalone `mcp_servers`, because those servers are not uniformly controlled by the feature gates Pervue can override. System-managed Codex policy remains an administrator-controlled trust input.
- **Workspace (SEC-02).** Codex runs in, and is pointed at with `-C`, an empty directory in the user's own cache: `~/Library/Caches/Pervue/codex-workspace` on macOS, `$XDG_CACHE_HOME/pervue/codex-workspace` or `~/.cache/pervue/codex-workspace` on other POSIX systems, `%LOCALAPPDATA%\Pervue\codex-workspace` on Windows. Codex follows instructions it finds where it runs: `AGENTS.md` in its working directory and, when a directory above it holds `.git`, in each directory from that one down. Checked with Codex CLI 0.156.1: with `.git` and an `AGENTS.md` two levels up, both that file and one in between reached the model. So anyone who can change the workspace, or any directory above it, can instruct the user's Codex. The workspace used to be `pervue-codex` in the system temporary directory, which on Linux is shared: another user could create it first, or add `.git` and `AGENTS.md` to `/tmp` itself.

  Before every launch, the host checks the workspace (`native/host/src/providers/codex/workspace.rs`). On POSIX, the workspace must be a directory of the user's own, not a link, and the host sets it to mode 0700. Every directory above it, both as named and with links resolved, must belong to the user or root and be writable by its owner alone; a sticky directory such as `/tmp` doesn't qualify. A directory of the user's may also be writable by the user's private group, as on Linux distributions that give each user one and a umask of 002: the user's primary group, named after the user, with no other members listed. Anyone else's group, or a shared one such as macOS's `staff`, doesn't qualify. Every link on the way must belong to the user or root, so no one else can have placed or replaced it, and Codex gets the resolved path, which is the one checked. The check reads owners and permission bits, not access-control lists. On Windows, reading access-control lists would need platform bindings: the workspace must be a directory, not a link or junction, and it is in `%LOCALAPPDATA%`, which Windows keeps private to the user. Without a cache directory, the host makes a new directory with a random name in the temporary directory, which passes only where that is private to the user, as on macOS and Windows. A workspace that can't be created, or that other users could change, stops Codex from starting (`PROVIDER_FAILED` / `WORKSPACE_UNAVAILABLE`).
- **Environment (SEC-02).** A provider process starts with an empty environment and gets only what the host passes on (`host/src/providers/environment.rs`): the user's home and name, the temporary directory, the text encoding, the session bus and runtime directory where Linux keyrings are found, network proxies, and extra CA certificates; on Windows, also what programs, `cmd.exe`, and Node need to run. The Codex adapter adds `CODEX_HOME`, `CODEX_SQLITE_HOME`, and `CODEX_CA_CERTIFICATE`, and sets `PATH` to Codex's own directory followed by the host's `PATH`. Nothing else reaches a provider. Credentials in the environment Chrome was started from, such as `OPENAI_API_KEY`, `CODEX_API_KEY`, `AWS_SECRET_ACCESS_KEY`, or `GITHUB_TOKEN`, stay behind, and so do variables that change how programs load code, such as `NODE_OPTIONS`, `LD_PRELOAD`, and `DYLD_INSERT_LIBRARIES`. Codex therefore signs in only with its stored login, the one its status check reports, however Chrome was started. Proxy settings are passed on because Codex can't reach its service without them; they can hold a proxy password, which Codex needs as much as the user's other tools do.
- `codex login status` prints the account and a masked key, so the adapter reads only its exit status. Codex's stderr and the messages of failed turns are discarded: the extension sees only fixed, normalized errors, and diagnostics record only codes and reasons.
- Pervue conversation IDs are random and map to Codex threads only inside the host and its private session files, so the extension never sees or chooses a Codex thread ID. A stored mapping is used only if it holds a valid thread ID. An unknown conversation ID never reaches Codex: without prior dialogue it fails as `INVALID_REQUEST` / `UNKNOWN_CONVERSATION` before Codex starts, and with prior dialogue Codex starts a new thread from that bounded, validated history (CON-03).
- `conversation.forget` deletes files, so its reach is narrow. The extension can only name a conversation; the host alone maps it to a session, and the conversation and session IDs are validated before they touch a path. The host then removes that mapping and only the provider files that name the session and record Pervue's private workspace as their working directory: Claude Code transcripts under `projects/`, and Codex `rollout-…` session files. Directories are walked without following symbolic links, a link is removed rather than its target, and nothing outside the provider's own directory (`$CLAUDE_CONFIG_DIR` or `~/.claude`, `$CODEX_HOME` or `~/.codex`) is touched.
Tests: `provider_ids_are_names_not_paths_or_commands` in `native/host/src/host.rs`; `a_relative_program_path_is_refused_before_anything_starts` and `arguments_are_kept_as_separate_elements` in `native/core/src/process.rs`; `path_comes_before_the_usual_locations_and_relative_entries_are_dropped` in `native/core/src/discovery.rs`; `only_listed_variables_are_inherited` in `native/host/src/providers/environment.rs`; in `native/host/src/providers/codex/workspace.rs`, `the_workspace_is_in_the_users_cache`, `the_workspace_is_created_for_its_user_alone`, `a_workspace_others_could_open_is_closed_to_them`, `a_workspace_that_is_a_link_or_someone_elses_is_refused`, `a_directory_above_that_others_can_change_is_refused` (sticky too), `links_on_the_way_are_resolved_and_checked_both_ways`, `only_the_user_and_root_are_trusted_above_the_workspace`, and `a_private_group_is_the_users_own_alone`; `a_process_gets_only_the_environment_its_spec_sets`, `each_argument_reaches_the_process_whole`, and `a_process_runs_in_the_directory_its_spec_names` in `native/test_provider/tests/process_manager.rs`; and in `native/test_provider/tests/codex_adapter.rs`, `a_question_streams_its_answer_and_opens_a_conversation` (the exact command line, and the question only on stdin), `codex_gets_only_the_environment_it_needs` (with secrets and `NODE_OPTIONS` in the host's environment), `codex_runs_in_its_own_workspace`, `codex_gets_the_workspace_s_real_path`, `a_workspace_that_cannot_be_made_stops_codex_from_starting`, `a_workspace_others_can_change_stops_codex_from_starting` (checked before every launch), `a_question_travels_through_the_host_as_protocol_events` (neither Codex's stderr nor the question reaches events or diagnostics), `failed_turns_map_to_normalized_errors`, and `an_unknown_conversation_fails_without_running_codex` (option-, path-, and thread-shaped conversation IDs never reach Codex).

## 4. Validation before work

- The host validates each request completely (framing, JSON syntax, envelope, version, method, and method payload) before routing it. Providers, where work starts, only ever receive validated, typed requests. Test: `invalid_requests_never_reach_a_provider` in `native/host/src/host.rs`.
- The extension checks a request's ID grammar, size, and serializability before the native port opens or is used. A request that fails any of these checks fails on its own; it can't close the port for other requests in flight. The ask bridge also refuses an empty question before building a request.

## 5. Diagnostics

The host's stderr diagnostics (OBS-01) record identifiers, timings, and normalized outcomes. They never copy request content: no prompt text, page context, other payload members, raw frames, or error messages. Nor do they copy anything a provider wrote: stderr, the sign-in check's output, and the messages of failed turns are discarded unread. Diagnostics go only to stderr, never into the stdout frames.

Identifiers are redacted (SEC-02): a record copies only identifiers Pervue made itself. A request ID, or a cancellation's target, is copied only in the shape the extension gives every request, `req_` and a random UUID in lowercase hex. A provider ID is copied only if the host serves that provider, and a conversation ID only if the host created that conversation. Anything else a request carries is written as `[redacted]`. Recognizing secrets by their format can't work, since any caller-chosen text could be one, such as a Google `ya29.` token or a password; so no text a caller chose reaches the log, except a UUID in that shape, and no request can forge or split a record. The extension's own logging records only that a callback failed, never its error message or stack (SEC-03).

Tests: `diagnostics_never_copy_request_content` and `identifiers_pervue_did_not_issue_are_redacted_in_diagnostics` in `native/host/src/host.rs`; `request_ids_are_kept_only_in_the_extensions_shape`, `identifiers_are_kept_only_when_the_host_issued_them`, and `identifiers_can_neither_forge_nor_split_a_record` in `native/host/src/diagnostics.rs`; `diagnostics_go_to_stderr_and_never_into_the_frames` in `native/host/tests/cli.rs`; the hostile matrix (`native/test_provider/tests/hostile_matrix.rs`), whose fake Codex writes a fake key to stderr in every case; and the live smoke test, which checks its output for credentials before printing it (TST-05).

## 6. Packaged trust boundaries and permissions (SEC-04)

Packaging keeps the browser/native identity boundary explicit on both supported desktop platforms:

- **Exact extension identity.** Both package builders accept only one 32-character Chrome extension ID using the browser's `a`–`p` alphabet. The native host generates the manifest allowlist itself, so installers do not construct arbitrary origins. macOS installs that generated manifest at Chrome's fixed system location. Windows installs it under `%LOCALAPPDATA%\\Pervue` and registers only `HKCU\\Software\\Google\\Chrome\\NativeMessagingHosts\\com.pervue.host`; its host path is the fixed relative filename `pervue-host.exe`, which Chrome resolves relative to the manifest.
- **No webpage-controlled installer paths.** Install destinations, host names, manifest names, and registry keys are package constants. Neither installer has a post-install command surface that consumes browser/page input. A provider ID from a request still selects only a compiled adapter; provider executable discovery remains platform-controlled as described above.
- **Credential-free release metadata.** macOS and Windows `build-info.json` contain only version/package version, architecture, paired extension ID, and source commit. Provider credentials remain in provider-owned stores. Package build scripts contain no provider API-key inputs, and uninstall removes only Pervue-owned host/manifest/registration files.
- **Minimum extension permissions.** The MV3 manifest currently requests `activeTab`, `contextMenus`, `nativeMessaging`, and `storage`. It declares no `host_permissions`, `optional_host_permissions`, or `externally_connectable` entry. HTTP/HTTPS content scripts are present to implement explicit selection/current-page capture; CTX-03/CTX-04 constrain when content is actually collected and sent.
- **Regression audit.** `packaging/security-audit.mjs` asserts the permission set and both package definitions on every CI run. The macOS and Windows package jobs separately exercise the installed Native Messaging registration and exact extension allowlist.

The remaining release-signing trust decision for Windows is distribution policy rather than an SEC-04 boundary requirement; a future Windows signing/reputation task can add Authenticode without changing these registration invariants.
